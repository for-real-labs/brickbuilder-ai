# Fable helpers

A helper is a function a build script calls to get a whole, ready-made piece of a model: `roof(...)`, `wheels(...)`, `tree(...)`. The model writes one line and the kit places parts that are already known to fit together. Helpers exist because models lose paid rounds on the same structures again and again (tree canopies, roof courses, loose steps, wheels that are not joined to anything).

## Where things are

| What | Where |
|---|---|
| One module per helper family | `backend/fable_agent/helpers/` (`trees.py`, `roofs.py`, `walls.py`, `windows.py`, `doors.py`, `arches.py`, `decks.py`, `stairs.py`, `railings.py`, `cars.py`, `vehicles.py`, `furniture.py`, `props.py`) |
| Shared building blocks | `backend/fable_agent/helpers/common.py`: argument checks, `Frame` (one layout, any facing), `bridge` (plates that span a gap), `column`, `tiles`, stocked colors |
| The registry | `backend/fable_agent/helpers/__init__.py`: `_MODULES`, `HELPERS`, `bind`, `prompt_section` |
| What the model is told | generated by `prompt_section()`, used in `assisted()` in `backend/fable_agent/prompts.py` |
| Tests on stand-in parts (run in CI) | `backend/tests/test_fable_helpers.py`, stand-ins in `backend/tests/fable_agent_support.py` (`HELPER_PARTS`) |
| Tests on real parts (skipped without a parts library) | `backend/tests/test_fable_helpers_real.py` |
| Documentation and the evidence behind the part choices | `docs/fable-helpers.md` |

A module exports `HELPER` (or `HELPERS` for several). Adding the module's name to `_MODULES` is all it takes to reach build scripts, the prompt and the registry tests. Nothing else lists helpers.

## Rules a helper must keep

1. **Use only the kit's public methods** (`place`, `fill`, `inset`, `attach`, `connect`, `stand`, `measure`, `part`, `footing`, `plain_part`, `stocked_color`, `has_part`). A helper must obey the same grid and checks as a hand-written script.
2. **Every part rests on studs of something the helper placed, or of what the caller put under it.** Say in the module's docstring why the construction holds: what rests on what. If a joint is not a stud joint (a wheel on a pin, a door in a frame), place the part with `kit.attach` or `kit.inset`, which record the joint, and take the offset from real models, not from memory. Something that stands on a surface without studs (tyres on a road) is joined with `kit.stand`. Record each joint between the two parts that really meet (brick to axle, axle to wheel, never brick to wheel): the v2 methods refuse a joint whose parts do not touch, and a Technic pin or axle that is in none of the other part's holes. They also refuse solid plastic in the same place whatever `allow_overlap` says, and need one building order for the whole model, so `test_every_style_builds_clean_with_real_parts` and `test_every_helper_can_be_built_in_small_connected_steps` hold every style to those rules.
3. **Never use a part or color that is not stocked.** Get colors through `stocked`, `need`, `brick_color` or `kit.plain_part`: they return the stocked color closest to the one asked for. When a style's key part is missing, raise `KitError` saying what the catalog lacks.
4. **Refuse clearly.** A size or style a helper cannot build raises `KitError` with what to change. A refused call must place nothing, so check arguments before the first placement.
5. **Styles are data.** A style is an entry in the module's `STYLES` table that one of a few constructions reads. Add a style by adding an entry; add a construction only when no existing one can build it.
6. **At least 15 styles per helper**, each visibly different. `test_every_helper_offers_at_least_fifteen_styles...` enforces this.
7. **Check where the parts end up, not only that the checks pass.** Parts placed with `attach` are not checked for overlap, so a wheel can sit inside the body and every check still passes. Assert positions in the tests: wheels even either side of the body, tyres on the ground, studs on the grid (`test_wheels_sit_evenly...` is the pattern).
8. **Keep saved builds working.** Scripts saved with a design call helpers by name and argument. Never rename a helper, a style or an argument, and never change what an existing style builds in a way that could break a model that used it. Add a new style instead.
9. **Only the v2 methods are told about helpers** (Pip and Thorough v2). The first versions' prompts must not change: `test_lean_v2_repairs_and_offers_trees_while_lean_stays_as_it_was` checks this.
10. **Helpers are a shortcut, not a fence.** The prompt tells the model to build by hand whatever no style can make. Do not remove that sentence, and do not make a helper the only way to build something.

## Adding a style

1. Find the parts. `docs/fable-helpers.md` lists which parts customers' models and official sets use, and where the evidence came from (customers' generations, the LDraw Official Model Repository, Rebrickable's published part lists). For a joint that is not a stud joint, look up how official sets seat that pair of parts before you trust any offset. Check the part is in the catalog and measure it with `kit.measure(part)`, `kit.part(part).studs` and `kit.footing(part)` rather than trusting a description.
2. Add the entry to the module's `STYLES`, with default colors that exist in the catalog.
3. If the model needs a fact to use it (the opening a window fills, a stair's tread), make sure the helper's `notes` give it. Keep notes to a few words: they are in every prompt.
4. Run the real-parts test. It builds every style at several sizes and facings and fails on any overlap, unattached part or unstocked part:

   ```sh
   cd backend && uv run --group dev pytest tests/test_fable_helpers_real.py -k "<helper> and <style>"
   ```

   This needs an LDraw library (`LDRAW_DIR` or `~/ldraw`). CI has none and skips it, so a style that was never run here has never been checked against real parts. Say so in the pull request if you could not run it.
5. Render it and look. A style can pass every check and still face the wrong way:

   ```sh
   printf 'fill(rect(-4,-4,20,20),0,"Green",kind="plate")\nroof(0,1,0,12,10,style="gambrel")\n' > /tmp/try.py
   cd backend && python -m fable_agent script /tmp/try.py --out /tmp/try --views front-right back-left
   ```

6. If the stand-in library lacks a part the style needs, add a block of the right size and studs to `HELPER_PARTS` and cover the style in `tests/test_fable_helpers.py`.

## Adding a helper

1. Decide whether it earns its place: it should be a structure that many builds need and that models get wrong, with evidence (failed revisions, or how often customers build it).
2. Write `helpers/<name>.py` with a docstring that explains the construction, a `STYLES` table, a `build_<name>(kit, x, y, z, ...)` function, and `HELPER = Helper(...)`. Follow the argument conventions: `(x, z)` is the min corner of the footprint, `y` the base in plates, `style`, colors, then `facing`.
3. Add it to `_MODULES`, add its name to the set in `test_every_helper_offers_at_least_fifteen_styles...`, and add its cases to `cases()` in `tests/test_fable_helpers_real.py`.
4. Add it to the table in `docs/fable-helpers.md`.

## Before you open the pull request

- `uv run --group dev pytest tests/test_fable_helpers.py tests/test_fable_helpers_real.py tests/test_fable_agent_assist.py`
- Measure what the prompt costs: the helper section is sent with every Pip and Thorough v2 build. Keep summaries and notes short.
- Record the change with the `agent-change-log` skill: a helper change changes how the Pip agent and Fable Thorough v2 behave, so each gets a document in `docs/agent-changes/`.
